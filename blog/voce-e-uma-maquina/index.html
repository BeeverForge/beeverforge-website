Are you a machine?The future of software developers in the age of AI

“You’re a machine” was a compliment for someone who could produce without slowing down. Now the machine writes the code. If a company judges engineers by how much they produce, it has already picked the work it will automate first.

From cards to conversation

Before programmers could type a program on a screen, they could write it on a stack of punched cards. The holes represented characters, and the computer read the cards in order. Today you can start by describing in words what you want the program to do.

  1. Punched cards

    A card could hold one line of a program. Running it meant taking the stack to a card reader. [1]

  2. Programming languages

    Code became the text colleagues read and maintained. Compilers and interpreters took care of running it.

  3. Vibe coding

    Describe what you want, try the result, and ask for changes. The code can stay out of the conversation. [2]

From chat to factory

Ask for a screen in chat and minutes later you have something to try. The next change brings a different job: turn the request into code, run the project’s tests, and check whether the result meets the agreed requirements. The ladder below shows how much of that process you can hand to the machine.

Industrializing means repeating that process for every change. At BeeverForge[4], a task comes in with acceptance criteria. The factory plans the change, implements it, runs the project checks, and sends it for independent review. The same workflow runs for each task. Other workflows can even ship changes to production without human approval for each release[6].

Will the company still need me?

To write every line of code, the company can already do without you. A team at StrongDM[7] took that idea literally. Engineers defined the specifications and test scenarios. Agents wrote the code and ran the checks. The team also did away with manual code review.

At BeeverForge, we already have software in production whose code was written entirely by agents. We use the same factory to maintain BeeverForge itself[8]. The people working on the project still decide what needs to change and what evidence would show that it worked.

Many teams have long divided the work this way. A business analyst identifies what the business needs and spells out its rules. A systems analyst turns those rules into requirements and describes how the software should behave. A developer implements those requirements and makes technical decisions along the way. From punched cards to vibe coding, the way we give instructions to machines has changed. With a software factory, agents can take on writing the implementation itself.

Robert C. Martin, better known as Uncle Bob[9], made a career teaching people to write better code. In a 2026 interview, the author of Clean Code said he now barely sees the generated code. He tells the agents what he wants and which constraints matter. Then he examines the architecture and tries the software to see how it behaves. Decades of writing code show up in the instructions he gives and in what he notices when he puts the system to the test.

Yes, there is work for developers who can turn requirements into a system that works in practice. If access must end as soon as a customer deletes their account, the engineer has to work out how to enforce that rule in the app, on the website, and across sessions that are already open. They also need a test that catches any session that still works. Frederick Brooks[5] already put system design and testing at the heart of software engineering. With implementation delegated, designing, testing, and investigating failures can take up more of the day.

Are you a machine?

“You’re a machine” was how we praised someone who delivered a lot and kept up the pace. If you learned to program that way, you know what makes you proud: seeing something work because you understood a problem nobody had managed to explain properly. Typing out the solution was part of that pleasure. Discovering it still is.

When the machine takes over the keyboard, you can spend more time on that work. Talk to the people who will use the software. Try out an architecture before committing the team to it. Write a test for the case everyone forgot. That’s how programmers make more room for engineering in their work.

Maybe we need to learn a different compliment: “I’m glad you spotted that before we built it.”
