Are you a machine?The future of software developers in the age of AI

“You’re a machine” was a compliment for someone who could keep up with production. Now that a machine can write the code, the compliment exposes a problem: we’ve spent too long judging engineers by how much implementation work they get through.

From punched cards to specifications

Punched cards were a way to feed instructions into a computer. With languages like Fortran[6], programmers could write formulas and leave the translation into machine instructions to the compiler. Source code had two audiences. The compiler needed precise instructions. The people maintaining the system needed to understand what their colleagues had done.

AI agents move part of that translation up another level. A team can specify the behavior and delegate writing the code line by line. It takes seconds to type “let users delete their accounts.” Deciding when access ends, what happens to the data, and how to prove the deletion worked takes engineering. This was the difficulty Frederick Brooks identified in No Silver Bullet[1]: working out what the system should do and testing it.

Will the company still need me?

If the job exists to turn specifications into code, the company may stop needing that job. An agent can already write the implementation and run the tests. An automated deployment[7] can ship the change to production without anyone reviewing the code or approving that release. The job of reading everything the machine writes may disappear too.

In 2025, the ILO and NASK study[3] estimated that one in four workers worldwide were in an occupation with some exposure to generative AI. It measures exposure at the task level, which helps explain why jobs with the same title may have different futures. A company may cut an implementation role. It may also need someone with the experience to design the architecture, write acceptance criteria, and investigate failures in production. That’s the answer for anyone who wrote the code and designed the system in the same role. The company can do without hand-written code and still need someone who can design the system and measure whether it works.

Where the engineering happens

Think about a bridge. Drafting each component takes skill. The design also has to establish what loads the bridge will bear, how to test it, and what signs would warrant closing it. In software, the same distinction comes up when a team decides how to divide a system, which tests need to pass, and what to measure in production to know whether a change worked. Code is a way to carry out those decisions. Part of engineering is making them and checking their effects.

In an interview with Aviator[2], Robert C. Martin described the shift in his own routine. With agents writing code, he pays more attention to architecture and system behavior. Experience as a programmer still matters here. It helps you see where a specification leaves room for a poor implementation and design a test that catches it before a user does.

What will we call productivity?

In Atlas of AI[4], Kate Crawford traces work that disappears from view when an interface returns an answer in seconds. In software, that work can reappear when someone investigates a failure or handles a customer complaint. Bruna Brito and I wrote in MIT Technology Review Brasil[5] about how platforms shape behavior through what they make visible. A team dashboard does something similar when it shows how many changes shipped and leaves out the cost of keeping them running.

If an agent ships ten changes on Monday, the dashboard records ten deliveries. The engineer who realizes three of them should never have been made might end the day without adding a line of code. If “you’re a machine” is still the compliment, the dashboard will side with the machine.
